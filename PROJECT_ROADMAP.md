# DzMoney 2.0 — MASTER ROADMAP

> **Single source of truth for the clean rebuild.** This roadmap replaces all previous roadmaps and old BUX-era assumptions. The project uses a new PostgreSQL database and must not reintroduce legacy BUX/core/compatibility business logic.

## Global implementation rules

- Backend/database is the source of truth; frontend never calculates authoritative balances or rewards.
- Every balance movement is atomic, idempotent and recorded in an auditable ledger.
- Admin settings must change real backend business rules, not only displayed values.
- Referral, Squad and Gaming are completely independent systems.
- Build and test one subsystem at a time.
- Do not carry obsolete BUX names, legacy fields or unexplained settings into the new system.
- Keep modules isolated so fixing one subsystem does not destabilize unrelated subsystems.
- **TON is an external reference/settlement currency only. The internal DzMoney economic reward/distribution currency is DZX.**
- **Reward Pool is removed from the product scope. Historical Reward Pool PRs/commits remain Git history only and must not be revived or assigned a replacement phase.**

# Phase 1 — Economy & Currency Core 🔒 SPECIFICATION COMPLETE

## Currencies

### COIN
Activity/reward currency. Earned from qualifying activity such as tasks and advertisements and from applicable referral or promotional rewards.

### DZX
**Main internal economic currency.** DZX is the currency used for economic rewards, applicable Promo rewards, deposits after TON conversion, campaign budgets and withdrawal accounting.

**Agreed DZX source model:**
- advertisements;
- tasks;
- referral earnings;
- deposits converted from TON;
- Promo rewards when the configured Promo reward is DZX.

**Squad is NOT a direct DZX source.** Squad only modifies an otherwise qualifying base activity reward by the configured percentage. The resulting reward must retain its original economic source and record the Squad modifier separately.

### DZP
**Package currency and activity indicator.** DZP is used to buy packages and earned activity DZP is used to measure qualifying activity where the product contract explicitly requires an activity measure.

### TON
External blockchain currency. TON is **not** an internal DzMoney wallet currency. It is used only as the external value/reference for deposits and withdrawals.

## Fixed economic relationship

**1 TON = 10,000 DZX = 10,000,000 COIN**

Therefore:

**1 DZX = 1,000 COIN**

## DZP conversion rates

**1,000 COIN = 1 DZP**

**10,000 COIN = 10 DZP**

**10 DZX = 1 DZP**

**100 DZX = 10 DZP**

Therefore:

**1 DZP = 10,000 COIN = 10 DZX**

## Conversion direction

Allowed:
- COIN → DZP
- DZX → DZP

Not allowed:
- DZP → COIN
- DZP → DZX

## DZP source separation

The ledger must distinguish at least:
- `earned_dzp` — obtained from qualifying activity;
- `converted_dzp` — obtained through COIN/DZX conversion;
- `purchased_dzp` — obtained through purchase/package-related acquisition.

Converted and purchased DZP are not earned activity.

## DZX source separation

The ledger must identify DZX by its true source. The agreed source set is:
- advertisements;
- tasks;
- referral earnings;
- deposits converted from TON;
- Promo rewards when the configured Promo reward is DZX.

Promo rewards may also be COIN. The reward currency is determined by the configured Promo campaign and must be recorded explicitly in the ledger.

**Squad is a modifier, not a source.** A Squad percentage can increase the reward generated by an eligible base activity, but it must never create an independent DZX source or be counted as a separate earning stream.

Source metadata must remain immutable in the ledger. A reward must retain its original source even when a Squad modifier changes its amount.

## Admin economy

Admin controls the configurable economic rates/settings. Changes affect the real backend/database logic. Historical transactions retain the rates that applied when they occurred; changing a rate must not rewrite past ledger records.

# Phase 2 — Activity, Ads & Tasks

## Standard default reward

**1,000 COIN + 1 DZX + 1 DZP**

This is the default reward for qualifying standard task/ad activity and is Admin-configurable.

**Squad modifier:** when the user's Squad conditions are satisfied, the configured Squad percentage modifies the applicable base reward. Squad does not create a new source.

## Verification contract for tasks

Every non-advertisement task in all task categories uses two explicit user actions:

1. **Execute** — performs the task/action required by the task.
2. **Verify** — submits the completion for server-side verification and reward eligibility.

The Verify action is advertisement-gated where configured: pressing Verify launches a short verification advertisement of **5 or 10 seconds**. The verification advertisement is part of the verification flow and does not grant an additional task reward.

The reward is issued only after the backend verifies task completion and the verification-ad requirement. Verification must be idempotent and cannot claim the same task reward twice.

This Execute → Verify model applies to:
- Daily Tasks;
- Game Tasks;
- Social Tasks;
- Web Tasks;
- Special/Partner Tasks.

**Advertisement tasks are excluded** because their own completion is the advertisement itself.

## Advertisements

Implement verified advertisement completion, reward idempotency, anti-duplicate protection and server-side reward issuance.

Separate:
- Tasks-page advertisements;
- Gaming advertisements, owned by Phase 5 Gaming;
- verification advertisements attached to task verification.

A verification ad must not be silently counted as a second task reward source. Gaming ads are not Task ads.

## Daily Check-in

Daily Check-in is advertisement-gated where configured: the user must complete the required advertisement before receiving the reward.

## Task categories

Strict category separation:
- Daily Tasks
- Game Tasks
- Social Tasks
- Web Tasks
- Special/Partner Tasks

A task cannot be created or validated under an incompatible category.

## User-created tasks

Available to normal users:
- Game
- Social
- Web

Partner/Special campaigns require contacting Admin.

Creator pays the task campaign cost.

Reference pricing:

**10 DZX per valid visit/execution. Equivalent CPM: 10,000 DZX per 1,000 valid visits/executions.**

The pricing model remains Admin-configurable through the existing campaign configuration/management architecture.

There is no separate Creator price for Click Proof versus Server Verified; the canonical unit price is 10 DZX per valid visit/execution.

Task lifecycle:

Draft → Pending Review → Active → Paused → Completed/Expired → Closed/Refunded

# Phase 3 — Referral System

Referral is a separate one-level lifetime system and is independent from Squad and Gaming.

## Qualification

A referred user qualifies after entering through the referral link and completing at least one qualifying activity:
- one verified advertisement; OR
- one verified task.

## Activation reward

**10,000 COIN + 10 DZX + 10 DZP**

The 10 DZP is granted once only at referral qualification.

## Lifetime earnings

Referrer receives **20%** from the referred user's qualifying daily base activity rewards.

The 20% applies only to the referred user's qualifying:
- task activity;
- advertisement activity.

It does NOT apply to:
- Squad modifiers/bonuses;
- Gaming rewards;
- Promo rewards;
- package multipliers;
- referral earnings themselves;
- other non-base activity income.

The one-time 10 DZP activation reward is not included in the lifetime 20% calculation. The lifetime calculation uses the applicable COIN + DZX activity reward portion before any Squad modifier.

# Phase 4 — Hierarchical Squad System

Squad is completely separate from Referral and Gaming.

## Hierarchy

Membership follows a tree/hierarchical structure. A newly qualified member is automatically attached to the Squad hierarchy of the member through whom the structure was formed.

Example:

```text
A ─── B ─── C
│          │
D ─── Y    X
```

No artificial global Squad member cap.

## Levels

- 10 levels.
- Admin defines the required member count for each level.
- Admin defines the bonus percentage for each level.
- Bonus is a percentage increase applied to an eligible base activity reward.
- Each level may have a different percentage.

## Daily activation

For day D, the system checks:

1. Required Squad member count for the relevant level is satisfied.
2. At least **50% of eligible Squad members** are active that day, where activity means at least one verified advertisement OR one verified task.

If and only if both conditions are satisfied, the Squad modifier is activated for **the following day (D+1)**.

If either condition fails, the modifier is inactive for D+1.

**Squad never becomes a separate DZX source.** It only modifies the amount of an eligible base activity reward. The underlying reward remains attributed to its original source, with the Squad percentage stored as modifier metadata.

Squad modifiers never enter the Referral 20% calculation as a separate earning stream.

# Phase 5 — Gaming 🎮

**Phase 5 is Gaming. Reward Pool is removed from the product scope and has no replacement phase.** The canonical Gaming contract is `docs/PHASE5_GAMING.md`.

Gaming is an independent subsystem and must reuse existing Economy, Ledger, Task and verified-ad boundaries rather than creating duplicate versions of them.

## Gaming resources

- Activity can produce Spin Progress and Axe Progress according to the finalized Gaming activity rules.
- **Spin Ticket** is used only by Spin.
- **Axe** opens a Digging session.
- **Energy** is used only for Digging and resets daily.
- Gaming resources are not internal Economy balances.

## Spin

- 1 claimed Spin activity = **+1 Spin**.
- Spins accumulate and do not expire during the day.
- 1 Spin creates exactly one server-side roll and one authoritative result.
- The wheel animation is presentation only; the server result is authoritative.
- A rare Jackpot is a distinct result and is not the same as No Reward.
- Reward weights are simulation inputs until the required economic simulation is completed and approved.

Initial simulation-only reward categories:
- 100 COIN
- 1,000 COIN
- 1 DZX
- 10 DZX
- 1 DZP
- 10 DZP
- +1 Spin
- No Reward
- rare Jackpot

No final economic weight is locked by this roadmap until simulation results are reviewed.

## Digging

- 1 Axe starts one Digging session.
- A new board is generated server-side once at session creation and persisted.
- The initial board contract is 16 tiles, subject to Admin configuration.
- Each new session starts with **3 Energy**.
- Each tile click consumes one Energy.
- The same tile can never be randomized again after it has been revealed.
- The saved board result is authoritative when the user returns later.

Digging reward categories:
- 100 COIN
- 1 DZX
- 1 DZP
- +1 Axe
- No Reward
- optional rare Jackpot

Initial simulation example for a 16-tile board: 10 No Reward, 3 × 100 COIN, 1 × 1 DZX, 1 × 1 DZP, 1 × Extra Axe. These are simulation inputs, not final economic values.

## Energy and reset

- Daily Digging Energy = **3**.
- Reset occurs at **00:00 UTC+1**.
- Energy changes 3 → 2 → 1 → 0 per revealed tile.
- At 0: **No more digs today**.
- The board/session persists when the user leaves and resumes when they return.

## Gaming Ads

Gaming ads are separate from Tasks-page ads and are never silently reclassified as Task rewards.

### Spin ads

- Verified ad → **+1 Spin** plus one independent random Ad Bonus.
- Spin ad progress is tracked independently.
- Example display: **23/100**.

### Digging ads

- Verified ad → Digging ad progress +1.
- Every 10 verified Digging ads → **+1 Axe** plus one independent random Ad Bonus.
- Digging ad progress is tracked independently.
- Example display: **18/100**.

### Ad Bonus

Ad Bonus is independent from the game result and may be:
- 100 COIN; or
- 1 DZX.

The Admin configures the weights. Ad limits are Admin-configurable; the initial simulation must test a possible 100-ad/day limit per Gaming game and its combined economic effect.

## Gaming Tasks

- Spin Task Claim → **+1 Spin**.
- Digging Task Claim → **+1 Axe**.
- A task claim must not ambiguously issue multiple overlapping activity/resource rewards.
- Existing Task Catalog → Task Execution → Verification → Reward boundaries remain authoritative.

## Activity

- Activity day boundary is **00:00 UTC+1**.
- Remaining daily activity resets at the boundary.
- Energy resets to 3/3 at the same boundary.
- Example: after 17 activities, remaining activity may be 7; after 20 it is 0. Remaining activity does not become an extra Spin/Axe unless the finalized Gaming activity contract explicitly says so.

## Admin configuration

Gaming Admin controls are versioned:

### General
- daily activity rules;
- daily ad limit;
- reset timezone;
- enabled/disabled.

### Spin
- reward set;
- weights;
- Jackpot configuration;
- enabled/disabled.

### Digging
- board size;
- daily Energy;
- reward set;
- weights;
- enabled/disabled.

### Ads
- Spin ad rewards;
- Digging ad rewards;
- Ad Bonus weights;
- per-game daily limits.

Every configuration change creates a new configuration Version.

Historical sessions retain the configuration version under which they started. An Admin change must not mutate an existing Spin roll or Digging board.

## Audit and idempotency

Gaming Session records at minimum:
- user;
- game;
- resource consumed;
- configuration version;
- result;
- reward;
- created_at;
- completed_at.

Gaming Ad records at minimum:
- user;
- game;
- verified ad reference;
- reward;
- resource progress;
- timestamp.

Repeated ad callbacks, Spin requests, tile clicks and Task claims must be idempotent and cannot duplicate rewards or resources.

## UX contract

Gaming Home:

**🎮 GAMING**
- 🎡 SPIN card with Spin resource;
- ⛏️ DIGGING card with Axe/Energy state.

Spin page order:

**Game → Gaming Ads → Tasks**

Digging page order:

**Game → Gaming Ads → Tasks**

The UI must remain mobile-first and accessible. Use semantic HTML (`main`, `section`, `article`, `button`, `nav`, `progress` where appropriate), CSS Grid for the Gaming Home and Digging board, modern CSS primitives, `:focus-visible`, accessible touch targets and `prefers-reduced-motion`. Do not introduce a UI framework unless repository evidence proves it necessary. Do not redesign unrelated DzMoney screens.

## Economic simulation gate

Before final reward values or weights are locked, simulate at least **1,000 users × 30 days** and measure:
- activities;
- Spins;
- Axes;
- ads;
- COIN emission;
- DZX emission;
- DZP emission;
- Jackpot frequency;
- extra Spin/Axe generation;
- average user reward;
- best/worst cases;
- total Gaming cost to Economy.

Architecture and UX may be implemented independently of final reward weights, but no economic configuration is considered final until the simulation has been reviewed.

# Phase 8 — Deposit System

External deposit currency: **TON**.

TON is not kept as an internal reward balance.

Flow:

**TON deposit → blockchain confirmation → automatic TON→DZX conversion → DZX credit**

Initial economic conversion:

**1 TON → 10,000 DZX**

The deposited TON itself is not credited as TON inside the application; the user's internal balance receives DZX after confirmation.

Deposited DZX is tracked separately from earned DZX and must follow internal withdrawability rules.

Every deposit requires:
- unique blockchain transaction reference;
- confirmation status;
- idempotency protection;
- immutable ledger entry;
- exact TON amount and resulting DZX amount recorded for audit;
- source marked as `deposit`.

# Phase 9 — Withdrawal System

Initial minimum withdrawal value:

**0.2 TON**

TON is the external settlement value. Internally, the withdrawal requirement is represented by DZX/COIN economics.

Initial eligibility requirements:

**2,000,000 COIN + 2,000 DZX**

These are configurable by Admin.

At withdrawal:

1. Verify the user satisfies the COIN and withdrawable DZX requirements.
2. Deduct **2,000,000 COIN + 2,000 DZX** atomically.
3. Treat the deducted economic value as the configured **0.2 TON** withdrawal value.
4. Send the external TON settlement to the user's wallet.

Withdrawal processing must be atomic, idempotent and ledger-backed.
