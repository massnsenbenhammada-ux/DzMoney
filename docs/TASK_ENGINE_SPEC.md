# DzMoney Task Engine v1 — Execution Specification

> **Status:** SPECIFICATION DRAFT — no Task Engine implementation is authorized until this document is reviewed and approved.
>
> **Primary source:** `PROJECT_ROADMAP.md` Phase 2 — Activity, Ads & Tasks.
>
> This document converts the roadmap requirements into an implementation contract. It does not introduce new economic rules unless explicitly marked as an implementation requirement.

---

## 1. Scope

Task Engine v1 covers:

- Daily Tasks
- Game Tasks
- Social Tasks
- Web Tasks
- Special/Partner Tasks
- user-created Game/Social/Web campaigns
- task execution and verification
- verification advertisements where configured
- server-side completion verification
- reward issuance and ledger recording
- idempotency and duplicate/replay protection
- task lifecycle and campaign accounting

Advertisement-only tasks are a separate activity type and are **not** forced through the Execute → Verify task model.

Out of scope for this phase:

- Referral implementation
- Squad implementation
- Reward Pool implementation
- Packages
- Withdrawal implementation
- unrelated frontend redesign

---

## 2. Economic Contract

### Standard qualifying activity reward

Default:

- `1,000 COIN`
- `1 DZX`
- `1 DZP`

The default is Admin-configurable.

The authoritative reward configuration lives in the backend/database, not in frontend JavaScript.

### Reward source

For a normal task completion, the economic source is `task`.

The ledger must preserve the original source. A future Squad modifier may change the amount but must never become a separate source.

### Activity DZP

Only DZP generated by qualifying activity is `earned_dzp` and contributes to Daily Activity / Reward Pool weighting according to the finalized Reward Pool rules.

Purchased, converted, transferred or deposited DZP is not reclassified as earned activity.

---

## 3. Task Categories

The category enum is strict:

```text
DAILY
GAME
SOCIAL
WEB
SPECIAL_PARTNER
```

A task must have exactly one category.

### User creation permissions

Normal users may create:

- GAME
- SOCIAL
- WEB

`SPECIAL_PARTNER` campaigns require Admin/Partner handling.

`DAILY` tasks are controlled by the platform/Admin and are not normal user-created campaigns.

The backend must enforce category permissions; the UI must not be the security boundary.

---

## 4. Task Lifecycle

Canonical lifecycle:

```text
DRAFT
  ↓
PENDING_REVIEW
  ↓
ACTIVE
  ↓
PAUSED
  ↓
COMPLETED / EXPIRED
  ↓
CLOSED / REFUNDED
```

### State rules

- `DRAFT`: editable by its authorized creator; not visible as an executable task.
- `PENDING_REVIEW`: submitted for Admin review; execution is disabled.
- `ACTIVE`: eligible users may execute the task.
- `PAUSED`: new executions are blocked; existing sessions are handled according to task expiry/session policy.
- `COMPLETED`: campaign/task has reached its completion condition.
- `EXPIRED`: task reached its configured expiry without completing normally.
- `CLOSED`: terminal administrative state.
- `REFUNDED`: terminal campaign-financial state where unused campaign budget is returned according to the campaign accounting rules.

No terminal state may silently become active again. Reopening, if ever required, must be an explicit authorized transition with an auditable event.

## 5. Execute → Verify Contract

Every **non-advertisement** task uses two explicit user actions.

### Step A — Execute

`Execute` performs or initiates the action required by the task.

Examples depend on category:

- Social: join/follow/engage with the configured destination.
- Web: visit the configured URL/action target.
- Game: perform the required game action.
- Daily: perform the configured daily action.
- Special/Partner: perform the configured partner action.

`Execute` alone never grants the task reward.

The backend may create an execution/session record when the task requires one.

### Step B — Verify

`Verify` submits the claimed completion to the backend.

The backend must:

1. authenticate the user;
2. verify the task exists and is currently eligible;
3. verify the user's campaign/task eligibility;
4. verify the required completion evidence/provider response;
5. enforce any configured verification-ad requirement;
6. enforce idempotency/replay protection;
7. atomically issue the reward exactly once;
8. record the reward in the ledger;
9. mark the completion as rewarded.

Frontend state must never be treated as proof of completion.

---

## 6. Verification Advertisement

A task may require a short verification advertisement when configured.

Allowed duration options from the roadmap:

- 5 seconds
- 10 seconds

The verification advertisement:

- belongs to the task verification flow;
- does not create a second task reward;
- does not create a second independent task activity event;
- must not be counted as a Reward Pool advertisement;
- must be distinguishable from ordinary Task-page advertisements.

Conceptually:

```text
Task completion
      +
verification ad
      ↓
ONE task reward
```

The backend must verify the provider callback/event before final reward issuance.

---

## 7. Advertisement Tasks

Advertisement tasks are excluded from the two-button Execute → Verify model because the advertisement itself is the activity.

They require their own verified-ad completion flow:

```text
Start ad
   ↓
Provider completion
   ↓
Trusted server verification
   ↓
Idempotency check
   ↓
ONE activity reward
```

Advertisement-task completions must remain distinguishable from:

- Task-page verification advertisements
- Reward Pool advertisements
- Daily Check-in advertisements

No cross-counting is permitted.

---

## 8. Verification Architecture

The Task Engine must use provider adapters rather than embedding provider-specific logic throughout task services.

Conceptual boundary:

```text
Task API
   ↓
Task Service
   ↓
Verification Service
   ↓
Provider Adapter
   ↓
External Provider
```

The Task Service must not depend directly on a specific ad provider implementation.

Provider-specific signatures, callback formats and validation rules belong inside the provider adapter/boundary.

A provider callback must be authenticated/validated server-side according to that provider's trusted mechanism before it can affect economic state.

---

## 9. Idempotency and Replay Protection

Reward issuance is exactly-once from the economic perspective, even if the same external completion is delivered multiple times.

Every completion/rewarding operation must have a stable idempotency identity derived from the authoritative task/user/provider completion context.

Required behavior:

```text
first valid completion  → reward once
same completion again   → no second reward
same idempotency key with different payload → reject
invalid/replayed event   → reject/no reward
```

The ledger and completion records must provide a durable uniqueness boundary. Application-memory flags are insufficient.

---

## 10. Reward Transaction

Task reward issuance must be atomic.

Conceptual transaction:

```text
BEGIN
  lock/validate completion
  validate eligibility
  create immutable ledger entries
  update authoritative balances
  mark completion rewarded
COMMIT
```

If any part fails, the complete reward operation must roll back.

A successful response must only be returned after the durable transaction succeeds.

---

## 11. Completion States

A task execution/completion record should distinguish at minimum:

```text
STARTED
PENDING_VERIFICATION
VERIFIED
REWARDED
REJECTED
EXPIRED
```

`VERIFIED` means the server has accepted the completion evidence.

`REWARDED` means the economic transaction has been committed.

A user must not receive the same reward twice because a completion remains in an intermediate state.

---

## 12. Eligibility and Limits

Eligibility must be checked server-side at verification time.

The checks must cover at least:

- task status is eligible;
- task has not expired;
- user is allowed to participate;
- campaign/task completion limit has not been exceeded;
- user-specific completion limit has not been exceeded;
- the completion has not already been rewarded;
- required verification evidence exists and is valid;
- required verification advertisement has been completed when configured;
- provider event has not been replayed.

Any additional frequency/cooldown rule must be explicitly configured and stored rather than invented in the frontend.

---

## 13. User-Created Campaign Accounting

The roadmap reference pricing is:

**1,000 valid visits/executions = 0.90 TON = 9,000 DZX**

The pricing model is scalable and Admin-configurable.

The creator pays the campaign cost.

Campaign budget accounting must be separate from user reward accounting. A campaign charge must not be mistaken for an earned user reward.

The implementation must define, before coding, whether campaign budget is reserved at creation, activation, execution, or another explicit point. The chosen rule must be documented and atomic.

Unused campaign funds and refunds must be represented by explicit financial records; no balance may be silently rewritten.

---

## 14. Admin Responsibilities

Admin must be able to control the real backend configuration for the task system, including where applicable:

- task activation/status;
- category and category-specific configuration;
- reward amount/currency;
- verification requirements;
- verification-ad requirement and allowed duration;
- task limits;
- campaign pricing;
- campaign review/approval;
- availability and expiry;
- ordering/display controls.

Admin UI values that do not change backend behavior are invalid and must not be presented as authoritative settings.

---

## 15. Anti-Fraud Boundaries

The following are mandatory architectural rules:

- Never trust a client-provided `reward` amount.
- Never trust client-provided completion status.
- Never let the frontend write balances.
- Never let a client choose the ledger source arbitrarily.
- Never accept an unsigned/unverified provider callback as economic proof.
- Never reward the same completion twice.
- Never count a verification ad as a second task reward.
- Never count Reward Pool ads as Task completions.
- Never mix advertisement-task, task-verification and Reward Pool activity identifiers.
- Never use application memory as the only duplicate-prevention mechanism.

---

## 16. API Boundary

The exact route names are intentionally **not fixed by this specification** until the current repository's HTTP architecture is reviewed.

The API must expose separate responsibilities for at least:

```text
Task discovery/listing
Task detail
Task execution/start
Task verification/claim
Provider callback/webhook
Admin task management
Campaign management
```

No route may directly manipulate wallet balances outside the established economy/ledger service boundary.

Provider callbacks must not call frontend code to complete rewards.

---

## 17. Data Model Boundary

The final schema must keep these concepts separate:

- task definition;
- task creator/campaign owner;
- task execution/session;
- task completion/verification;
- provider event/idempotency identity;
- campaign budget/accounting;
- reward transaction/ledger entry.

A single overloaded table must not become the source of truth for unrelated concepts.

Historical task reward records must preserve the configuration/source that actually produced them.

---

## 18. Observability and Audit

Every economically relevant task event must be traceable to:

- user;
- task;
- category;
- campaign where applicable;
- completion/execution identity;
- provider event identity where applicable;
- reward source;
- reward amount/currency;
- timestamp;
- verification outcome.

Failed verification must not silently disappear.

Economic records must remain immutable; corrections use compensating/auditable records rather than rewriting history.

---

## 19. Test Gate Before Implementation Is Considered Complete

The Task Engine cannot be marked complete until automated tests cover at least:

### Happy path

- execute → verify → reward;
- advertisement completion → reward;
- verification-ad flow → one reward.

### Duplicate/replay

- duplicate verify;
- duplicate provider callback;
- same idempotency key with same payload;
- same idempotency key with conflicting payload;
- replayed old provider event.

### Eligibility

- inactive task;
- paused task;
- expired task;
- completed campaign;
- exceeded user limit;
- exceeded campaign limit;
- unauthorized category/creator action.

### Atomicity

- reward transaction rollback;
- concurrent verification attempts;
- concurrent provider callbacks;
- ledger/balance consistency after failure.

### Separation

- Task ad does not count as Reward Pool ad;
- verification ad does not create a second task reward;
- Reward Pool ad does not count as Task activity;
- source attribution remains `task` for task rewards.

### Security

- forged client reward amount;
- forged completion state;
- invalid provider signature/callback;
- unauthorized admin mutation;
- cross-user completion/replay attempt.

## 21. Explicit Non-Goals / Anti-Drift Rules

The following must not be introduced while implementing Task Engine v1 unless this specification is explicitly revised first:

- Squad logic inside Task Service;
- Referral calculations inside Task Service;
- Reward Pool distribution logic inside Task Service;
- package multipliers directly modifying task reward amounts;
- frontend-authoritative rewards;
- provider-specific code scattered through unrelated services;
- duplicate task engines or parallel `v1/v2` implementations;
- legacy BUX compatibility logic;
- modifying old migrations instead of adding a new migration;
- hardcoded economic configuration that Admin is supposed to control.
